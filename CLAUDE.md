# CLAUDE.md — template-automation (Brannock Web)

## Business problem

Podimetrics makes the SmartMat, a device that captures daily thermal scans of diabetic patients' feet. Before the scan pipeline can detect temperature elevations (which indicate potential foot ulcers), each patient needs a **foot template** — a binary foot-shaped mask that tells the system where the feet are in the raw thermogram.

This application is the tool clinical operations staff use to create those templates. The operator selects a patient, reviews their scans, builds a template (either automatically or by manually stacking scans), places 6 anatomical keypoints on the result, and saves. The save event triggers reprocessing of all of that patient's scans against the new template.

This was previously a Python/Qt desktop app (`brannock.py`) using numpy, scipy, and matplotlib. This project is the web migration — a React SPA that delegates the heavy computation to server-side APIs while keeping the interactive template-review and keypoint-placement workflow in the browser.

## End-to-end workflow

### 1. Authentication

- User visits `/` → redirected to `/login` if no session token, or `/brannock` if authenticated.
- Login POSTs to `/api/v1/sessions/` with `{ user_id, password }`. The returned `session_id` is stored in `localStorage['__podi']` and used as a Bearer token for all subsequent API calls.
- On 403 from any API call, the token is cleared and the user is redirected to `/login`.
- **LOCAL mode**: any email/password logs in with a mock token. All service functions return mock data — no backend needed.

### 2. Patient selection (`PatientSelector`)

- On mount, two queries fire in parallel:
  - `GET /api/v1/patients/` → returns an S3 pre-signed URL → fetched for the actual patient JSON array.
  - `GET /api/v1/templates/metadata` → returns scan count metadata for filtering (3 JSON maps merged into one response).
- The operator can filter patients via 4 checkboxes:
  - **Show Demo** (default OFF) — when off, hides patients with affiliations containing `p04` or `demo` (case-insensitive, null-safe).
  - **Requires Template** — shows only patients with >= 4 scans and no existing template.
  - **Single Foot** — shows only patients flagged as single-foot.
  - **Has Single Foot Scan** — shows two-feet patients that have some single-foot scans.
- A text search performs fuzzy token matching (substring-based, scored by % of query tokens matched) and sorts results by similarity. Without search text, patients sort alphabetically by last name.
- Results are capped at 10. The selected patient ID is persisted to the URL search param `?patientId=`.

### 3. Scan selection (`ScanSelector`)

- When a patient is selected, the scan list loads via `GET {patient.scans_url}?scan_type=user&start_date=2024-10-01&end_date={today}`.
- Scans without `mat_thermogram_url` or with `schema_id === 9` (SmartMat Plus scans) are excluded.
- Each scan row has two independent interactions:
  - **Checkbox** — toggles the scan into the `selectedScanIds` set (used for build).
  - **Row click** — selects the scan for thermogram preview (highlighted blue).

### 4. Template build (`BuildControls` → server)

Two modes, both delegated to the server:

- **Auto Build** — enabled when a patient is selected. Uses checked scans if any, otherwise the server picks up to 14 recent scans. The server runs `template.build_templates()` (iterative mask extraction, Pearson similarity matching, scipy optimization).
- **Manual Build** — enabled when >= 4 scans are checked. The server runs `cleats.templates.stack_thermograms()` (affine registration via differential evolution).

Request: `POST /api/v1/templates/build` with `{ patient_id, scan_ids, mode: 'auto' | 'manual' }`.
Response: `{ left_foot, right_foot, left_threshold, right_threshold, earliest_scan_id, date_created, foot_side }`.

Build takes 5–30 seconds. The UI shows a spinner during the mutation.

### 5. Template review (`TemplateCanvas`)

- The build response populates one or two `<canvas>` elements rendered as heatmaps (copper palette, threshold-based alpha masking).
- Canvases are laid out in anatomical convention: right foot on the left, left foot on the right.
- **Single-foot results** show only one canvas. `FootSideControls` let the operator change the assigned foot side or rotate 180°.
- **Manual mode** shows `ThresholdSliders` (1–99%, default 40%) that re-render the heatmap in real time.

### 6. Keypoint placement (`KeypointSelector` + `TemplateCanvas` click)

- The operator selects one of 6 anatomical keypoints from a list: Hallux, 1st/3rd/5th Metatarsal Head, Arch, Heel.
- Clicking on a template canvas places a marker at normalized (0–1) coordinates for that keypoint on that foot side.
- Green dots in the keypoint list indicate placed keypoints. The header shows progress (e.g., "4/6").
- For bilateral templates, each keypoint needs both left and right coordinates. For single-foot, only the active side.

### 7. Save (`SaveTemplateButton` → server)

Before save, the button validates:
1. A template exists (left, right, or both).
2. All required keypoints are placed per the foot configuration.

On save, two transforms are applied to match the legacy event format:
- **Y-flip on keypoints**: `y = 1 - y` (canvas origin is top-left; template expects bottom-left).
- **Horizontal flip on template arrays**: each row is reversed (equivalent to `numpy.fliplr`).

The save payload matches the legacy cloud storage event shape:

```json
{
  "which": "patient_template_defined",
  "what": {
    "patient_id": "d48dce...",
    "left_foot": [[0.0, ...], ...],
    "right_foot": [[0.0, ...], ...],
    "left_threshold": 0.4,
    "right_threshold": 0.4,
    "keypoints": {
      "Hallux": {
        "left_normalized_coordinate": { "x": 0.26, "y": 0.13 },
        "right_normalized_coordinate": { "x": 0.67, "y": 0.14 }
      },
      "1st Metatarsal Head": { ... },
      "3rd Metatarsal Head": { ... },
      "5th Metatarsal Head": { ... },
      "Arch": { ... },
      "Heel": { ... }
    },
    "earliest_scan_id": "20250301...",
    "date_created": "2025-03-01T..."
  }
}
```

`earliest_scan_id` and `date_created` are included only when available (auto-build provides them).

On success, all build state is cleared and the UI resets for the next patient.

## State management

All state lives in the `BrannockPage` component (`src/routes/brannock.tsx`). There is no global state library.

| State | Managed by | Scope |
|---|---|---|
| Server data (patients, scans, thermograms) | TanStack Query (`useQuery`) | Cached, deduped |
| Build + save operations | TanStack Query (`useMutation`) | Transient |
| Selected patient ID | URL search param (`patientId`) | Survives page refresh |
| Scan checkboxes, preview scan, templates, keypoints, thresholds, foot side, active keypoint | `useState` in `BrannockPage` | Transient — cleared on patient change or save |

TanStack Query keys:
- `['brannock-patients']`
- `['brannock-metadata']`
- `['brannock-scans', patientId]`
- `['brannock-thermogram', matThermogramUrl]` (staleTime: Infinity — thermograms are immutable)

## Patterns and conventions

- **Path alias**: `@/` maps to `src/`. All imports use this.
- **Service ↔ mock boundary**: every service function checks `ENV.ENV === 'LOCAL'` at the top and returns mock data if true. This is the only conditional — no feature flags or test doubles elsewhere.
- **Schemas for types, not validation**: Zod schemas in `src/schemas/` define data shapes and produce TypeScript types via `z.infer`. They are NOT used for runtime API response validation.
- **Const tuples for enums**: `export const X = [...] as const; export type X = (typeof X)[number];`
- **Formatting**: Prettier with single quotes, semicolons, 160 char width, no trailing commas, Tailwind class sorting.
- **`routeTree.gen.ts`**: auto-generated by the TanStack Router Vite plugin. Never edit manually.
- **Component style**: functional components with `FC<Props>`, Tailwind for all styling, `cn()` for conditional class merging.

## Legacy context

This app replaces `brannock.py`, a single-file Python/Qt desktop application. The heavy computation (template building, thermogram stacking, scipy optimization) has been moved server-side. The web app handles:
- Patient/scan selection and filtering
- Template visualization (heatmap rendering on HTML5 Canvas)
- Interactive keypoint placement (click-to-place on canvas)
- Coordinate transforms and event payload construction for save

The `template` and `cleats` Python libraries that contain the build algorithms are external to this repo. The backend team exposes them through the `/api/v1/templates/build` endpoint.
